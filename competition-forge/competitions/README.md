# 赛道机制 · 怎么让一套工具服务多个比赛

## 为什么要分赛道

不同赛事的评价体系不是"同一份东西换个封面"。同一个项目：

- 投**大创** → 你要证明"这笔钱给我，我能按期做出东西" → 评委看可行性、经费、进度、团队
- 投**大挑** → 你要证明"我已经做出了有价值的成果" → 评委看选题、方法、数据、社会效益

写法反了就是硬伤。按大创的写法做大挑，会死在"没有真调研"；按大挑的写法做大创，会死在"不像个项目"。

所以本技能把「赛事差异」抽成独立的赛道档案，工具链（`pf` 命令、图表、排版、生图）**共用一套**。

## 三层结构

```
competition-forge/
├── SKILL.md                    ← 主控：第零步强制定赛道 + 六阶段通用流程
├── competitions/               ← 赛道层：每个比赛一套判断标准
│   ├── registry.md             ← 注册表（先查这个）
│   ├── README.md               ← 本文件
│   ├── dachuang/               ← 大创
│   │   ├── PROFILE.md          ← 评审偏好、骨架、字数、失分点
│   │   ├── cases.md            ← 往年案例
│   │   └── ppt.md              ← 该赛道 PPT 策略
│   └── datiao/                 ← 大挑
├── ppt/PLAYBOOK.md             ← PPT 编排层（调 ppt-master）
├── figures/                    ← 科研绘图 + AI 生图
├── scripts/                    ← pf 工具链（与赛道无关，全赛道共用）
├── references/                 ← 通用方法（排版、文献、去 AI 味…）
└── templates/                  ← 章节骨架（按赛道分）
```

**关键分工**：

| 层 | 管什么 | 谁维护 |
|---|---|---|
| `SKILL.md` | 流程骨架、硬规则、什么时候读什么 | 本项目 |
| `competitions/<id>/` | 这个比赛特有的一切判断 | 本项目，随比赛增加 |
| `scripts/` `references/` | 与比赛无关的通用能力 | 本项目，稳定 |
| `ppt-master` | PPT 怎么生成（SVG→DrawingML、模板、动画） | **上游项目，不复制** |
| 本机 SD / AGNES | 图片怎么生成 | 外部能力，本技能只调用 |

## 调用时序（每次都必须走）

```
① 用户提出需求
   ↓
② 定赛道 ── 用户说了就直接用；没说就按线索猜一个再确认；没建就新建
   ↓
③ 读 competitions/<id>/PROFILE.md ── 拿到该赛道的评审口径
   ↓
④ 按六阶段流程做（文档 / 图 / 排版 / 文献）
   ↓
⑤ 要 PPT → 读 ppt/PLAYBOOK.md → 调 ppt-master
   ↓
⑥ 交付自检（pf qa + 本赛道验收清单）
```

## 新增赛道

### 什么时候建

用户要用一个新比赛，且**至少要有一份真实材料**（官方模板、往年案例、评审规则）才开始建。
没有材料就只建空壳，是自欺欺人——写出来的"评审偏好"全是编的。

### 建什么

```
competitions/<id>/
├── PROFILE.md    ← 必须有
├── cases.md      ← 有案例才写，没有就写"暂无，待补充"
└── ppt.md        ← 有答辩环节才写，没有就写明"该赛道不需要 PPT"并说明原因
```

### PROFILE.md 模板

```markdown
# <赛道官方全称>（<简称>）

## 一、这个比赛是什么
主办方 / 层级（国家级·省级·校级）/ 面向谁 / 一年几次 / 关键时间节点

## 二、评委怎么打分
评审维度与权重（有官方规则就照抄，没有就写"据往年经验归纳，待核实"）

## 三、材料形态
必须交什么 / 字数 / 页数 / 格式 / 要不要 PPT / 要不要附件

## 四、章节骨架
逐节列出，标注每节该写什么、大概多少字

## 五、常见失分点
按严重程度排，每条写"为什么会失分 + 怎么避免"

## 六、与其他赛道的区别
最容易搞混的地方，明确写出来
```

### cases.md 怎么写才不是抄

往年案例的价值是**学写法**，不是搬内容。每条案例按这个结构写：

```markdown
### <案例标题>（<年份> <获奖等级>）

**选题**：讲的是什么问题
**为什么能获奖**：评审看重的那一点是什么（这是核心，不是复述内容）
**可迁移的做法**：结构怎么搭 / 数据怎么呈现 / 论证怎么闭环
**不可迁移的部分**：它的具体数据、地域、结论，我们用不了
```

**绝对禁止**：把案例里的数据、结论、图表搬进自己的材料。这是学术不端，也是比赛直接淘汰项。

## 维护规则

1. 新增赛道 → 在 `registry.md` 加一行 → 在 `D:\AI\AI-Hub\INDEX.md` 登记
2. 赛道档案改动 → 更新 `CHANGELOG.md`
3. 每年比赛规则变了 → 更新 `PROFILE.md` 并标注核实日期，**不要把旧规则当现行规则用**
4. 所有"评审偏好"类的判断，能指回官方文件就指回，指不回就标"据往年经验归纳"
